# Архитектура BB Kiosk

- Статус: актуально
- Владелец: engineering
- Последняя сверка с кодом: 18 августа 2026 года

## Назначение системы

BB Kiosk обслуживает гостевой заказ за столом, вызовы официанта и контроль статуса
приготовления. В монорепозитории находятся киоск, приложение официанта, API,
Android-оболочки и iikoFront Bridge.

## Компоненты

```text
┌────────────────┐      HTTPS       ┌──────────────────┐
│ Киоск / QR web │ ───────────────▶ │                  │
└────────────────┘                  │                  │
                                    │ Node.js API      │──▶ PostgreSQL
┌────────────────┐      HTTPS/WSS   │ 127.0.0.1:3107   │
│ Waiter web/APK │ ───────────────▶ │                  │
└────────────────┘                  └────────┬─────────┘
                                             │ HTTPS
                                             ▼
                                      iiko Cloud API
                                             ▲
                                             │ WSS
                                      iikoFront Bridge
```

Nginx завершает TLS, раздаёт обе web-сборки и проксирует `/api/` и WSS в Node.js.
API слушает только loopback-интерфейс. PostgreSQL не публикуется в интернет.

## Источники истины

| Данные | Источник истины | Локальное хранение |
| --- | --- | --- |
| Название, цена, вес, описание, КБЖУ, аллергены | внешнее меню iiko | снимок `iiko_menu_items` |
| Модификаторы | группы модификаторов iiko | снимок вместе с меню |
| Доступность | стоп-лист iiko | `iiko_stop_list_items` |
| Столы и залы | iiko | `iiko_tables` |
| Статус кухни | iiko webhook, резервный серверный опрос | `iiko_orders` и история |
| Фото, кадрирование, бейдж, состав, рекомендации | админка BB Kiosk по `restaurant_id + SKU` | `iiko_product_presentations` |
| Баннеры, QR-коды, терминалы, промокоды | BB Kiosk | PostgreSQL и `uploads/` |
| Заказ гостя | BB Kiosk до отправки, затем iiko | `customer_orders` |
| Сотрудники iikoFront | iikoFront Bridge | снимок без PIN |

SKU — стабильный ключ локального оформления между сезонными версиями меню. Меню
без SKU или с повторяющимися SKU не публикуется; продолжает работать последний
корректный снимок.

## Основные потоки

### Создание заказа

1. Клиент получает `/api/v1/bootstrap` и выбирает позиции.
2. Перед отправкой создаётся устойчивый `client_request_id`.
3. API повторно читает актуальное меню, модификаторы, стоп-лист и стол.
4. Сервер вычисляет стоимость, резервирует idempotency key и отправляет заказ в
   iiko с детерминированным UUID.
5. Ответ сохраняется в PostgreSQL. Повтор с тем же ID и телом возвращает прежний
   результат, а повтор с другим телом отклоняется.

### Статус заказа

iiko webhook является основным источником. API отвечает на webhook до выполнения
дополнительных сетевых запросов и обновляет снимок заказа в PostgreSQL. Каждые две
минуты сервер пакетно сверяет не завершённые заказы как защиту от пропущенного
события. Клиенты читают только локальный снимок.

### Меню и стоп-лист

Серверная задача раз в десять минут обновляет меню, столы и стоп-лист. Стоп-лист
дополнительно обновляется по webhook и резервно раз в две минуты. Одновременный
запуск общей синхронизации заблокирован флагом `backgroundSyncRunning`.

### Вызов официанта

Киоск создаёт service request. Приложение официанта получает очередь из API и push
через Firebase. Статусы запроса: `new` → `accepted` → `in_progress` → `completed`.

## Рестораны и изоляция

Таблицы содержат `restaurant_id`, а терминал и QR проверяются в контексте текущей
организации. Однако один запущенный экземпляр API сейчас держит одну активную
конфигурацию iiko в памяти. Для нескольких ресторанов безопасная схема — отдельный
deployment/API на ресторан. Общий multi-tenant runtime потребует отдельной работы:
разнести runtime-конфигурацию, фоновые задачи, кеши и Firebase-аудит по tenant ID.

## Границы безопасности

- iiko credentials, Firebase Admin key и ключ шифрования существуют только на
  сервере;
- `VITE_*` считается публичным и не используется для секретов;
- webhook проверяется отдельным токеном;
- iikoFront Bridge устанавливает только исходящее WSS-соединение;
- PIN iiko проверяется внутри iikoFront и не сохраняется API;
- загружаемые изображения проверяются по MIME-сигнатуре и ограничены 8 МБ;
- административные операции пишутся в audit log.

## Технические ограничения

- API — один Node.js-процесс; горизонтальное масштабирование потребует вынести
  in-memory блокировки и bridge registry во внешний координационный слой;
- локальные uploads и OTA должны находиться на общем хранилище при нескольких API;
- миграции сейчас выполняются перед перезапуском и требуют совместимости назад;
- Android package ID сохраняет исторический namespace и не меняется без отдельной
  миграции установленных устройств.
