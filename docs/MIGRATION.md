# Перенос BB Kiosk в GitLab и на новый сервер

Документ описывает перенос без потери заказов, изображений, настроек iiko, QR-кодов и OTA. Секреты в репозиторий не копируются.

## Текущее состояние перед переносом

- Основная ветка: `main`.
- Runtime проекта и CI: Node.js 22 или новее.
- База данных: PostgreSQL 16.
- Web/API: Nginx → Node.js systemd service → PostgreSQL.
- Изменяемые данные: PostgreSQL, `uploads/`, OTA-архивы и серверный `.env`.
- Firebase Android client config находится в `waiter/google-services.json`. Это публичная конфигурация APK, а не Firebase Admin-ключ. API-ключ должен быть ограничен пакетом `ru.zvyak.brooklynbowl.waiter` и сертификатом подписи в Google Cloud.

## Перенос репозитория в группу GitLab

1. Запретить новые изменения на время переноса и убедиться, что `git status` чистый.
2. Создать контрольный тег и отправить `main` с тегами в резервный GitHub.
3. Перенести существующий личный GitLab-проект в группу либо отправить все ветки и теги в пустой групповой проект.
4. Проверить, что число коммитов, ветки и теги совпадают локально и в GitLab.
5. Добавить участников команды и защитить `main`: обычные изменения только через Merge Request.
6. Перенести секреты в GitLab CI/CD Variables. Не копировать их в `.gitlab-ci.yml` или документацию.
7. После успешной проверки GitLab оставить GitHub read-only резервом минимум на две недели.

Переменные инфраструктуры, которые потребуются группе:

- `PUBLIC_APP_URL`;
- `DEPLOY_HOST`;
- `DEPLOY_USER`;
- `DEPLOY_WEB_ROOT`;
- `DEPLOY_API_ROOT`;
- `DEPLOY_SSH_PRIVATE_KEY` — protected file variable;
- `SSH_KNOWN_HOSTS` — protected file variable.

Переменные для нативных сборок:

- `ANDROID_KEYSTORE_PATH` — protected file variable с постоянным release-keystore;
- `ANDROID_KEYSTORE_PASSWORD` — masked/protected;
- `ANDROID_KEY_ALIAS` — protected;
- `ANDROID_KEY_PASSWORD` — masked/protected;
- `IIKO_LICENSE_MODULE_ID` — protected, используется при сборке iikoFront-плагина.

Без Android signing variables pipeline формирует только устанавливаемые debug APK. Release APK создаются и проверяются через `apksigner` только при наличии полного комплекта защищённых переменных. Постоянный keystore необходимо хранить ещё и в отдельном защищённом backup: потеря ключа исключит обновление уже установленного APK поверх существующего приложения.

Секреты самого приложения (`DATABASE_URL`, `TOKEN_SECRET`, `ADMIN_PASSWORD_HASH`, `IIKO_CONFIG_ENCRYPTION_KEY`) хранятся на сервере в `/etc/bb-kiosk-api.env` с правами `0600`, а не в GitLab, если деплой не создаёт сервер с нуля.

## Требования к новому серверу

Рекомендуемая базовая конфигурация для одного ресторана:

- Ubuntu 24.04 LTS;
- 2–4 vCPU, 4–8 ГБ RAM;
- от 40 ГБ SSD с отдельным контролем заполнения;
- Node.js 22 LTS;
- PostgreSQL 16 или новее;
- Nginx, Certbot, `rsync`, `curl`, `jq`, PostgreSQL client;
- отдельный deploy-пользователь с SSH-ключом;
- закрытый PostgreSQL, наружу открыты только 80/443 и ограниченный SSH;
- автоматические security updates, fail2ban и внешний backup.

## Что обязательно переносится

1. PostgreSQL custom dump из `/var/backups/bb-kiosk-postgres`.
2. `/var/www/bb-kiosk/uploads/` — баннеры и локальные изображения карточек.
3. `/var/www/bb-kiosk/ota/` — версии, которые уже могут быть установлены на планшетах.
4. `/etc/bb-kiosk-api.env` — только по защищённому каналу, с правами `0600`.
5. Nginx-конфигурация, systemd units, health/backup timers.
6. Действующие TLS-настройки либо новый сертификат после переключения DNS.

## Безопасный порядок переезда сервера

### 1. Подготовка

- Снизить DNS TTL до 300 секунд минимум за сутки до переключения.
- Поднять новый сервер параллельно со старым.
- Установить зависимости и развернуть код, не меняя DNS.
- Настроить PostgreSQL, firewall, Nginx, systemd, backup и мониторинг.
- Перенести предварительный дамп БД, `uploads/` и `ota/`.

### 2. Проверка до переключения

- Проверить `/api/v1/health/ready` через временный hostname или локальный `Host` override.
- Проверить bootstrap, меню, столы и стоп-лист без создания заказа.
- Проверить вход в админку и приложение официанта.
- Проверить Firebase Admin initialization и регистрацию устройства.
- Проверить исходящее соединение iiko Cloud и WSS iikoFront Bridge.
- Проверить ручную OTA-проверку киоска и официанта.
- Проверить сохранность QR-кодов: токены зависят от `TOKEN_SECRET`, поэтому он переносится без генерации нового значения.

### 3. Финальное переключение

Для текущего масштаба безопаснее короткое окно обслуживания, чем два одновременно пишущих сервера:

1. Остановить создание новых заказов на старом API.
2. Создать финальный проверенный `pg_dump`.
3. Восстановить его на новом PostgreSQL.
4. Выполнить `node migrate.mjs` на новом сервере.
5. Повторно синхронизировать `uploads/` и `ota/`.
6. Запустить API и проверить readiness.
7. Переключить DNS.
8. Проверить реальный тестовый заказ, его статус, вызов официанта и push.
9. Оставить старый сервер выключенным для записи, но доступным для rollback минимум 72 часа.

### 4. Webhook и внешние интеграции

Если публичный домен сохраняется, URL webhook iiko не меняется — после DNS-переключения нужно только подтвердить доставку событий. Если меняется домен, необходимо:

- обновить `PUBLIC_APP_URL`;
- перевыпустить/перерегистрировать iiko webhook;
- обновить OTA URL в Capacitor-конфигурациях;
- обновить QR-коды или настроить постоянный redirect со старого домена;
- обновить CORS/Nginx и ссылки в README.

## Проверка после переезда

- `systemctl is-active bb-kiosk-api`;
- readiness API и PostgreSQL latency;
- актуальность меню и стоп-листа iiko;
- тестовый заказ и смена всех статусов;
- четыре типа вызова официанта;
- Firebase push в фоне и при закрытом приложении;
- WSS iikoFront Bridge и синхронизация сотрудников;
- ручное OTA киоска и официанта;
- загрузка/отдача баннера и изображения блюда;
- ежедневный backup и проверка восстановления;
- Telegram alert и recover-сообщение;
- заполнение диска, журнал Nginx и systemd.

## Rollback

Если критичная проверка не проходит, DNS возвращается на старый сервер. Перед возвратом необходимо определить, успели ли появиться заказы на новом сервере: их нельзя потерять или повторно отправить в iiko. Старый сервер не должен принимать запись одновременно с новым.

## Ротация доступов

После успешного переноса перевыпускаются ранее использовавшиеся временные доступы:

- GitLab Personal Access Token;
- deploy SSH key;
- iiko API key / Client Secret;
- Firebase Admin service account;
- серверный пароль root, если он когда-либо передавался вручную.

Ротация `TOKEN_SECRET` и `IIKO_CONFIG_ENCRYPTION_KEY` без отдельной миграции запрещена: первый подписывает QR и сессии, второй расшифровывает настройки iiko и Telegram в PostgreSQL.
