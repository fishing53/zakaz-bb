# Безопасность

- Статус: актуально
- Последняя сверка: 19 августа 2026 года

## Модель доступа

- `administrator` управляет рестораном, интеграциями и безопасностью;
- `hostess` просматривает заказы и назначает столы терминалам;
- `terminal_manager` управляет только конкретным планшетом;
- `waiter` работает с очередью заказов и вызовов.

Персональные пароли хранятся как salted `scrypt`. `ADMIN_PASSWORD_HASH` —
bootstrap-доступ старой схемы и хранится только на сервере. После пяти неверных
попыток вход с IP временно блокируется.

## Секреты

| Секрет | Место хранения |
| --- | --- |
| PostgreSQL URL и token secret | `/etc/bb-kiosk-api.env`, `0600` |
| Ключ шифрования настроек | `/etc/bb-kiosk-api.env`, `0600` |
| iiko credentials и webhook token | PostgreSQL, AES-256-GCM |
| Telegram bot token | PostgreSQL, AES-256-GCM |
| Firebase Admin service account | отдельный серверный JSON, не Git |
| Deploy и signing keys | protected GitLab CI/CD Variables |

Выделенный CI runner принимает job только этого проекта, использует эфемерные
Docker-контейнеры и не совмещён с production. Shared runners проекта отключены.
Runner registration token и временный GitLab PAT не хранятся в репозитории.

`waiter/google-services.json` является клиентской Firebase-конфигурацией, а не
Admin key. API-ключ в ней должен быть ограничен Android package и сертификатом
подписи в Google Cloud.

Никогда не помещайте секрет в переменную `VITE_*`: Vite встраивает её в публичный
JavaScript.

## Сетевая модель

- наружу публикуются только HTTPS и ограниченный SSH;
- Node.js и PostgreSQL слушают внутренние интерфейсы;
- Nginx завершает TLS и ограничивает размер запросов;
- iikoFront Bridge создаёт исходящее WSS-соединение, входящий порт ресторана не
  нужен;
- strong-name ключ iikoFront Bridge хранится локально и в скрытой protected
  GitLab-переменной; в репозиторий и artifacts попадает только подписанная DLL;
- CORS разрешает production, Capacitor localhost и временный старый домен только
  для совместимости уже выпущенных APK.

## Входящие данные

- webhook iiko проверяется токеном;
- QR содержит подписанный сервером токен и версию;
- заказ пересчитывается сервером по актуальной БД;
- `client_request_id` защищает от дублей;
- изображения ограничены 8 МБ и проверяются по сигнатуре PNG/JPEG/WebP;
- административные действия записываются в audit log;
- Cloud API вызывается только сервером с rate limit и backoff.

## Ротация

После передачи временного доступа ротируются root-пароль, GitLab PAT/deploy key,
iiko Client Secret и Firebase Admin service account. Android release keystore не
ротируется без стратегии обновления установленной базы.

Не меняйте `TOKEN_SECRET` или `IIKO_CONFIG_ENCRYPTION_KEY` простым редактированием
env. Для первого нужна стратегия перевыпуска сессий и QR, для второго — миграция
зашифрованных данных.

## Реакция на инцидент

1. Ограничить или остановить затронутый канал, не удаляя журналы.
2. Зафиксировать время, компонент, correlation ID и затронутые заказы.
3. Отозвать скомпрометированный ключ у его провайдера.
4. Выпустить новый ключ и обновить server/CI secret store.
5. Проверить audit log, systemd journal, Nginx и iiko webhook history.
6. Проверить отсутствие повторных заказов перед повторной отправкой.
7. Задокументировать причину и добавить регрессионную проверку.

## Контроль перед релизом

- gitleaks не находит секретов;
- dependency audit не содержит неисправленных критических уязвимостей;
- TLS-сертификат и DNS валидны;
- backup создан и проверен через `pg_restore --list`;
- административные и waiter endpoints требуют правильную роль;
- webhook с неверным токеном получает отказ;
- production `.env` и Firebase Admin JSON имеют минимальные права.

Инфраструктурные IP, пароли и временные токены не являются документацией проекта и
хранятся отдельно от репозитория.
