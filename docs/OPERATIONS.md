# Эксплуатация BrooklynBowl Kiosk

## Заказы и защита от дублей

Перед отправкой киоск создаёт `client_request_id` и хранит его до подтверждённого ответа. Сервер атомарно резервирует значение в `order_requests`. Повторный запрос с тем же составом возвращает уже созданный заказ; попытка использовать ID с другим составом отклоняется.

Для iiko из `restaurant_id + client_request_id` формируется стабильный UUID, поэтому повтор после сетевого таймаута не должен создавать второй заказ в iiko.

## Сезонные меню

Источником названия, цены, состава, модификаторов и доступности остаётся iiko. Локальное оформление хранится в `iiko_product_presentations` по связке `restaurant_id + SKU`:

- фото;
- кадрирование;
- бейдж;
- SKU рекомендаций «Идеально с».

Баннер хранит `product_sku`; актуальный `productId` определяется при выдаче меню. При новом сезонном меню оформление автоматически прикрепится к позиции с тем же SKU.

Сервер не публикует новый снимок, если у видимой позиции отсутствует SKU или SKU повторяется. Предыдущее корректное меню продолжает работать.

## Роли

- `administrator` — полное управление рестораном;
- `hostess` — просмотр заказов и настройка терминала/стола;
- `terminal_manager` — только конкретный планшет;
- `waiter` — очередь заказов и вызовов.

Персональные администраторы и хостес создаются во вкладке «Сотрудники». Пароли хранятся как salted `scrypt`; старые PIN официантов продолжают работать и переходят на `scrypt` после смены.

После пяти неверных попыток вход блокируется для IP на 15 минут.

## Резервные копии

`zakaz-backup.timer` ежедневно запускает проверяемый `pg_dump` в `/var/backups/zakaz-postgres`. Хранятся 14 дней, для каждого дампа создаётся SHA-256. Проверка:

```bash
systemctl status zakaz-backup.timer
systemctl start zakaz-backup.service
journalctl -u zakaz-backup.service -n 50 --no-pager
ls -lh /var/backups/zakaz-postgres
```

Локальный backup защищает от ошибки приложения/БД, но не от потери всего сервера. Для промышленной эксплуатации каталог нужно дополнительно копировать во внешнее объектное хранилище.

## Мониторинг

Readiness endpoint:

```text
GET /api/v1/health/ready
```

Он проверяет PostgreSQL, наличие активного снимка меню, состояние синхронизации и backoff iiko. `zakaz-health.timer` запускает проверку каждые пять минут и дополнительно контролирует заполнение диска.

В веб-админке во вкладке «Проверка iiko» отображаются:

- доступность и аптайм API;
- задержка ответа PostgreSQL;
- ошибки создания заказов iiko за 24 часа;
- ошибки и последние события webhook;
- заполнение диска;
- ошибки фоновой синхронизации iiko и актуальность снимка меню.

Ошибки заказов и обработки webhook сохраняются в `monitoring_events`. Таймер забирает новые критичные события ровно один раз и передаёт их в настроенный канал оповещений.

### Защищённая настройка iiko

В этом же разделе администратор может переподключить ресторан без SSH. Перед доступом требуется повторно ввести свой пароль; дополнительный токен действует пять минут. Хостес и администратор конкретного терминала доступа не имеют.

Мастер запрашивает только доступные ресторану данные: `App ID`, `API Login` и `Client Secret`. После авторизации сервер сам получает из iiko список организаций, терминальных групп, внешних меню и обычный тип заказа. Если вариантов несколько, администратор выбирает ресторан, кассу и меню по названию — технические UUID вводить и копировать не требуется. Адрес Cloud API, источник заказа и webhook задаются сервером автоматически.

App ID, API Login, Client Secret и Webhook Token зашифрованы в PostgreSQL через AES-256-GCM. Ключ `IIKO_CONFIG_ENCRYPTION_KEY` хранится только в `/etc/zakaz-api.env` с правами `0600`. API никогда не возвращает сохранённые секреты в браузер: пустое поле означает «оставить прежнее значение». При первом подключении сервер создаёт webhook-токен, регистрирует адрес и подписки в iiko, затем перечитывает настройки для проверки. Ручное копирование токена не требуется.

Новая конфигурация проходит проверку авторизации, организации, внешнего меню, столов, типа заказа и стоп-листа. Применение разрешается только для неизменённого набора проверенных полей. После сохранения сервер регистрирует webhook и обновляет кэш; если любой этап не удался, предыдущие настройки webhook и рабочая конфигурация восстанавливаются.

Если в `/etc/zakaz-api.env` задан `ALERT_WEBHOOK_URL`, ошибка будет отправлена туда JSON-запросом. Без webhook ошибка остаётся в systemd journal:

```bash
systemctl status zakaz-health.timer
journalctl -u zakaz-health.service -n 50 --no-pager
```
