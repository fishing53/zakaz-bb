# Эксплуатация BB Kiosk

- Статус: актуально
- Владелец: operations / engineering
- Последняя сверка: 18 августа 2026 года

## Ежедневная проверка

```bash
systemctl is-active bb-kiosk-api
systemctl is-active bb-kiosk-backup.timer
systemctl is-active bb-kiosk-health.timer
curl -fsS https://order.brooklynbowl.ru/api/v1/health/ready
df -h
```

Readiness проверяет PostgreSQL, активный снимок меню и состояние iiko backoff. В
админке «Проверка iiko» дополнительно видны задержка БД, возраст меню, webhook,
ошибки заказов, стоп-лист и заполнение диска.

## Журналы

```bash
journalctl -u bb-kiosk-api.service -n 200 --no-pager
journalctl -u bb-kiosk-health.service -n 100 --no-pager
journalctl -u bb-kiosk-backup.service -n 100 --no-pager
```

При ошибке заказа сохраните время, номер заказа и correlation ID. Не отправляйте
заказ повторно, пока не проверены `customer_orders`, `iiko_orders` и iikoFront.

## Резервные копии

`bb-kiosk-backup.timer` ежедневно запускает custom-format `pg_dump`, проверяет его
через `pg_restore --list`, создаёт SHA-256 и хранит локальные копии 14 дней.

```bash
systemctl status bb-kiosk-backup.timer
systemctl start bb-kiosk-backup.service
ls -lh /var/backups/bb-kiosk-postgres
sha256sum -c /var/backups/bb-kiosk-postgres/<file>.sha256
pg_restore --list /var/backups/bb-kiosk-postgres/<file>.dump >/dev/null
```

Локальная копия не защищает от потери сервера. PostgreSQL dump, `uploads/`, OTA и
release keystore должны копироваться во внешнее хранилище. Не реже раза в месяц
восстанавливайте последний dump в отдельную БД и фиксируйте результат.

## Мониторинг и уведомления

`bb-kiosk-health.timer` запускается каждые пять минут и контролирует API,
PostgreSQL, меню и диск. Ошибки заказов, webhook и синхронизации записываются в
`monitoring_events`.

Telegram настраивается в «Безопасность»: bot token, Chat ID, включение и тестовое
сообщение. Токен шифруется и не возвращается браузеру. Повтор одного открытого
события ограничен; после восстановления отправляется recover-сообщение.

Падение самого сервера должно отслеживаться внешним мониторингом. Встроенный timer
не может уведомить, если хост полностью недоступен.

## iiko

Cloud API webhook — основной источник статусов и стоп-листа. Фоновые серверные
задачи сверяют меню/столы раз в десять минут, активные заказы и стоп-лист — раз в
две минуты. Планшеты не вызывают iiko напрямую.

При `429` не запускайте повторную ручную синхронизацию. Проверьте `Retry-After` и
состояние backoff. При недоступной терминальной группе новые заказы останавливаются,
но последний корректный снимок меню остаётся доступным для диагностики.

### Ошибка создания заказа

1. Найти событие `iiko_order` и correlation ID.
2. Проверить `is_alive` терминальной группы и стоп-лист.
3. Проверить, появился ли заказ в iiko до ручного повтора.
4. Проверить webhook `TableOrderError` и command status.
5. Если заказ создан в iiko, связать/восстановить локальный статус вместо создания
   второго заказа.

### Зависший статус

1. Проверить последнее событие `TableOrderUpdate`.
2. Проверить, что кухонный экран и места приготовления настроены в iiko.
3. Проверить фоновую синхронизацию активных заказов.
4. Не включать polling с каждого планшета.

## Smoke и нагрузка

Безопасная кнопка проверки не создаёт заказ: она проверяет API, БД, меню, SKU,
столы, стоп-лист, webhook, backup и Telegram.

Smoke-тест iiko создаёт настоящий заказ с отключённой сервисной печатью. Запускать
только на согласованном столе. Нагрузочная проверка ограничена и не обращается к
iiko; удалённый запуск требует `ALLOW_REMOTE_LOAD_TEST=YES`.

## Сезонное меню

iiko остаётся источником рабочих данных. Локальное оформление связывается по
`restaurant_id + SKU`. Перед публикацией сезонного меню проверьте уникальность SKU,
фото и рекомендации. Баннер ссылается на SKU и получает актуальный product ID при
выдаче bootstrap.

## QR-заказ

QR разрешается через `POST /api/v1/qr/resolve`. Сервер проверяет подпись, версию,
активность, организацию и актуальный iiko table ID. Отключение кода прекращает
новые заказы и вызовы; перевыпуск инвалидирует старую распечатку.

## Выдача Android-приложений

Подписанные `BB-Kiosk-latest.apk`, `BB-Waiter-latest.apk` и `manifest.json`
публикуются CI в `APPLICATION_DOWNLOAD_DIR`. В разделе «Приложения» администратор
выпускает одноразовую ссылку с ограниченным сроком действия. Просмотр страницы
установки не расходует ссылку; первое фактическое скачивание переводит выдачу в
статус `downloaded` и автоматически создаёт следующий QR. Повторная докачка с
того же IP и User-Agent разрешена 15 минут.

Android не сообщает веб-серверу результат установки APK. После проверки
устройства администратор вручную переводит скачанную выдачу в `installed`.
Не подменяйте APK вне CI: версия и контрольные суммы записываются в manifest при
публикации release-сборок.

## iikoFront Bridge

Проверьте исходящее WSS, `last_seen_at`, `last_sync_at` и версию bridge в админке.
PIN не хранится сервером: проверка выполняется установленным iikoFront. При замене
терминала создайте новый одноразовый pairing code и отзовите старый bridge.
